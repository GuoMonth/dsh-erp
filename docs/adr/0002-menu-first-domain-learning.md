# ADR 0002：菜单认知先行，再形成业务域认知与双向关联

日期：2026-09-11。状态：已接受。

本决策补充 [ADR 0001](0001-local-first-ai-erp.md) 的学习策略，不改变 Node 24、SQLite、本机浏览器和 dsh 原生代理的技术基线。执行范围见 [第一版规划](../v1-plan.md)，模型和状态的权威定义见 [学习模型](../learning-model.md)。

## 背景

仅由用户最初提出的任务驱动学习，容易形成局部认知。ERP 的业务过程可能跨越多个菜单；在缺少全局入口地图时，AI 容易遗漏关联环节。反过来，直接把菜单名称归类为业务域，也会把界面组织方式误当成真实业务结构。

需要先保留可观察的菜单事实，再根据页面证据形成业务理解，并长期维护二者的映射。

## 对抗式审查与决定

| 质疑 | 决定 |
| --- | --- |
| 只看一个业务域如何理解跨域流程？ | 首版在一个 ERP、一个角色下做全局 L1/L2 探索，再选择一个领域做 L3/L4 验证 |
| 全局探索会不会无限等待？ | 使用有范围、有预算、可恢复的探索轮次；阻塞和暂停形成部分成果，不能伪装为完成 |
| 是否必须全部页面学完才能推理？ | 每轮先积累结构和页面证据，再更新业务假设；不要求所有深层行为验证完成 |
| 一级菜单是否就是业务域？ | 分别维护菜单认知与业务域认知，允许多对多、有证据的关联 |
| 找到按钮是否等于学会操作？ | 结构层次与认知状态独立；发现、观察、解释、验证分开 |
| 图谱是否只是漂亮的总结？ | 业务结论必须能回到菜单入口和观察证据，缺失环节明确展示 |
| 是否每项知识都要询问用户？ | 自动学习与验证，关键歧义、冲突和业务写入才要求必要介入 |
| 文档或 Zod 是否可独自承载全部知识？ | 结构化记录为权威来源；描述、证据和不确定性保留，Schema 校验不代表语义或授权正确 |
| 是否将所有方法都预写成固定命令？ | AI 自主探索，成功方法生成能力候选，验证后复用；首版不增加独立 CLI 产品 |

## 已接受的决策

1. 学习主线为菜单结构认知、页面证据积累、业务域认知、双向关联和持续深化。
2. 首次全局结构探索是产品默认起点；用户可随时查看部分成果或中断，未完成范围不得隐藏。
3. 菜单认知模型与业务域认知模型独立维护；可执行能力作为第三类资产，关联其依赖的页面、规则及证据。
4. 四级探索先广后深：全局入口、功能结构、页面细节、业务行为。层次不等于真实菜单级数。
5. 业务假设可以指导下一轮探索，不能据此改写原始观察或自动确认业务关系。
6. 首个产品里程碑为当前角色全局菜单地图、初步业务域框架及可追溯双向关联。写入验证保留在首版后续阶段。
7. 菜单或规则变化按依赖关系触发局部复核，保留历史证据，不默认全部清空或全部继续有效。
8. 效果验收增加菜单结构、跨域关联、证据回溯和变化恢复；用对照任务验证全局探索的收益及首次投入成本。

## 后果与边界

首次认知需要额外时间和模型调用，换取后续任务的全局背景；收益必须实测。当前角色可见范围不等于整个 ERP 的功能全集，覆盖率不能以未知功能为分母。隐含写入、权限限制或无法到达的页面允许标记为阻塞，不为追求覆盖率执行未批准变更。

Schema 优先和可调用能力的借鉴以模型契约形式落地，不新增图数据库、CLI 服务或强制 Zod 依赖。现有 ADR 0001 中“初次只做有限勘察、由任务主导”的学习条目由本决策替代，其技术选型和效果优先例外仍有效。
